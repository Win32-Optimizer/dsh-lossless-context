**深入原理：为什么"归档 + 检索"能无损，而"摘要"不能**  
**1. 摘要为什么必然丢东西**  
看 DSH 内置压缩给摘要模型的指令（dsh-compaction-basic 源码里的 COMPACTION_INSTRUCTION）：  
Output EXACTLY the Markdown structure below: keep every section, in order.  
 Use terse bullets, not prose paragraphs.  
 ...  
 - If the conversation already contains a <compacted-summary> block, it is a PRIOR checkpoint.  
   Do not copy it forward verbatim: preserve still-true facts, drop stale ones,  
   and merge newer information into a single consolidated summary under the same structure.  
   
三件事决定了它一定是有损的：  
1. **"terse bullets"** — 输出被要求是精简要点，不是原文。  
2. **"drop stale ones"** — 明确要求丢掉"过时"的信息。问题是谁来判断"过时"？是摘要模型，它没有你的上下文。  
3. **反复合并** — 第二次压缩会把旧摘要再压一遍。信息 **指数级衰减**：第一次丢 20%，第二次在剩 80% 里再丢 20%，第五次只剩 33%。  
而且摘要还会丢掉这几类最要命的东西：  
- **被否决的方案**（"本来想用 MongoDB，因为事务问题否了"）——摘要倾向只留结论，不留否决理由  
- **当时的措辞**（"先确认再动手"和"操作前必须先确认"语气、约束强度不同）  
- **具体的数字和路径**（端口 5433、config/db.yaml）——容易被概括成"配置了数据库"  
- **情绪和犹豫**（角色扮演、咨询场景里这些恰恰是核心）  
**所以：摘要可以当导航，不能当记忆。**

**2. 归档为什么是无损的**  
openseek-lcm 的机制（读 lib/store.js 与 lib/messages.js 可以验证）：  
DSH 会话事件 (session/event, {global:true})  
     │  
     ├─ 过滤：跳过 harness 注入的消息（runtime-context / lcm-recall / system-prompt …）  
     │        —— 否则插件会把自己的输出再归档一遍  
     │  
     ├─ 超大块外移：> 60000 字符的 block → artifacts 表（按内容哈希去重）  
     │  
     └─ 逐字写入 messages 表  
          │  
          ├─ 建 FTS5 索引（CJK bigram / 拉丁 trigram）  
          └─ 构建摘要树（summary_nodes，用于导航，不是用来替代原文）  
   
关键点：  
- **压缩（compaction）不去碰这个库。** 压缩只改 DSH 的「surface」（发给模型的上下文），归档是独立 SQLite 文件。  
- **归档被当作派生缓存。** 插件的 ensureCaptured() 会比对 live session 的 seq 与归档 watermark，落后就用 ctx.sessionQuery.readSession() 重放补齐。 **漏捕能自愈。**  
- **原文源头是 DSH 的追加式会话日志**（<DSH_HOME>/sessions/**/session.*.jsonl*）。就算插件彻底坏了，原文还在那里。

**3. 检索凭什么能精确命中**  
**3.1 索引结构：n-gram，不是分词**  
上游 opencode-lcm 用 FTS5 默认的 unicode61 分词器，会把一整串汉字当作一个 token —— 无损上下文记忆 用 上下文 搜不到。  
   
 换成 trigram 分词器能修中文，但会让**两字词**失效，而两字正是中文词的常态长度（召回、诊断、记忆、索引）。  
openseek-lcm 的做法：**把文本改写成按文种定长的有序 n-gram（CJK 用 bigram，拉丁用 trigram），再用 ** **unicode61** ** 索引这些 gram。**  
   
 于是"子串是否出现"变成"这串 gram 是否相邻出现"——对拉丁子串和两字中文词同时成立。  
分词器声明为 unicode61 tokenchars '_'，所以 store_path 这类标识符的下划线保留。  
**3.2 候选用 OR，精度交给重排**  
自然语言查询如果每个词都 AND，会否掉几乎所有相关消息。所以：  
- FTS 查询用 **OR** 收集候选（带引号的组用 AND）  
- 再由 JS 重排器对**原文**核对，按 token 覆盖、短语命中、角色、新旧程度排序  
**3.3 三层 scope**  
| | | |  
|-|-|-|  
| **scope** | **范围** | **用途** |   
| session | 当前会话 | 默认，最便宜 |   
| root | 当前会话所在的分支树（parentSession 链） | 找 fork 出去的分支 |   
| worktree | **同一工作目录下**的所有会话 | 跨会话找回（换会话不丢记忆） |   
| all | 归档里所有会话 | 面向人的 /lcm 命令总能用；面向模型的 lcm_grep 默认拒绝（allowScopeAll: false），避免把别的项目的对话拉进来 |

**4. 压缩之后，模型怎么知道该去哪找**  
dsh-compaction-basic 在追加 compaction/summary 事件时，会带上 shadowedRange {start,end}、shadowedSeqs、shadowedTokenCount。  
openseek-lcm 监听这个事件，在**压缩后的第一轮**通过 agent/pre-step 注入一条有界的「压缩指针」：  
被移除的消息数、seq 区间、token 估算  
 + 回到原文的确切路径：lcm_expand 对区间内的摘要节点，或 lcm_grep --scope session  
 + resume note  
   
**这是确定性的查找，不是检索。** 它不依赖 automaticRetrieval.enabled，每次压缩只投递一次。  
（automaticRetrieval 是可选的逐轮相似度召回，默认关闭——DSH 把运行时上下文作为单独一条 user 消息发出，旧版锚点选择会把它误当查询词，导致召回的全是 harness 样板文本。测出来的数字：74 个候选、3 条注入，全是别的轮次里一模一样的 envelope。）

**5. 缓存为什么是省钱的大头**  
DeepSeek 的上下文硬盘缓存（[官方文档）：](https://api-docs.deepseek.com/zh-cn/guides/kv_cache "https://api-docs.deepseek.com/zh-cn/guides/kv_cache")  
- 默认开启，无需改代码  
- 命中前提：本次请求的**前缀**与之前落盘过的「缓存前缀单元」 **完整匹配**  
- 落盘时机：① 每次请求的"用户输入结束位置"和"模型输出结束位置"各产生一个单元；② 检测到多次请求的公共前缀时落盘该前缀；③ 长输入/输出按固定 token 间隔截取  
- 返回里看 usage.prompt_cache_hit_tokens / prompt_cache_miss_tokens  
价格（deepseek-flash，高峰）：命中 ¥0.04/M vs 未命中 ¥2/M —— **1/50**。  
**所以本方案在配置上刻意做三件"缓存友好"的事**：  
1. **工具白名单固定**（只留 5 个 lcm 工具）。工具表每轮都挂在请求上，一变就影响前缀。  
2. **抖动源放在末尾**。DSH 把运行时上下文作为单独一条 user 消息追加在最后，不塞进 system —— 对前缀友好。  
3. **稀疏压缩**。每次压缩都会让「第一个被替换的 token 之后」的缓存失效，所以宁可一次压掉一大段，也不要频繁小压。

**6. 为什么"在场记录"（AGENTS.md §3）是必要的补充**  
这是这套方案最反直觉的一点：**归档做到了无损，但体验上仍可能"像白板"。**  
原因在机制差异：  
| | | |  
|-|-|-|  
|   | **全量在上下文** | **归档 + 检索** |   
| 记忆形态 | 全部摆在眼前 | 只在被查询命中时出现 |   
| 想起来的成本 | 0 | 先意识到该查 → 发起检索 → 读回来 |   
| 想起的内容 | 全部，含氛围 | 只有精确命中的那 1–2 条 |   
| 连贯性 | 天然 | 断的 |   
   
**检索能给"事实"，给不了"在场感"。**  
弥补方式：把 8–15 段**原文片段**（不是总结）写进 AGENTS.md。它每轮都在、命中缓存后几乎不花钱（约 ¥0.0002/轮），却让模型"手里握着那些时刻"，而不是"知道有这回事"。  
这是目前唯一能在 1M 窗口限制下，同时拿到"省钱"和"人味"的做法。

**7. 如果要做成插件（写给想继续折腾的人）**  
本方案是**配置 + 工具层**，没有改 DSH 源码。如果想做成一个真正的一体化插件，DSH 的扩展点是这样对应的：  
| | | |  
|-|-|-|  
| **想要的能力** | **当前用什么实现** | **插件化可以用** |   
| 过滤 harness 注入消息 | openseek-lcm 的 INJECTED_SOURCE_KINDS | session/event 监听 |   
| 压缩后注入指针 | agent/pre-step | 同上 |   
| 伪造/改写请求上下文 | — | agent/request 扩展点 |   
| 提示词小节 | ctx.systemPrompt.section({name, order}) | — |   
| 工具注册 | ctx.tools.register() | — |   
| 命令注册 | ctx.inject(['commands'], …) | — |   
   
坑（都是实测踩过的）：  
- ctx.effect()**必须**在 apply() 的同步路径上调用，await 之后调用会导致整个 fiber 失败。  
- session/event 和 agent/pre-step 是**按 agent/session 作用域**派发的，插件自己的 context 上注册要带 { global: true }。  
- 改**插件代码**必须 **完整重启应用**（Cordis 加载器保留它首次导入的模块代际）；改 **配置值**重载即可。  
- Windows 下 pnpm 会把 \\server\share 形式的路径改写成损坏的相对符号链接，安装插件请用盘符路径。

**8. 这套方案测不出来的东西**  
诚实列一下已知的空白：  
1. **"该查却没查"的概率**。这取决于模型判断，没有可量化的指标。缓解手段是 AGENTS.md 里写死触发词，但无法证明 100% 生效。  
2. **长跑稳定性**。归档库在 DSH 主进程里长期运行的稳定性只做了功能验证，没有做数月级别的观察。  
3. **多设备一致性**。本方案假设单机使用。sessions/ 目录名由工作目录编码而来，换路径后 worktree scope 会切不到旧会话（session / root 仍可用）。  
4. **压缩对"人味"的长期影响**。可观测到的是"检索命中率"，不可观测的是"模型是否还像那个人"。这只能靠人来判断。
