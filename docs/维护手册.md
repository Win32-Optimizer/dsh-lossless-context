# 维护手册

> 给半年后的你自己看的。目标：**出了问题能自己定位，想调参数知道改哪个数字，想换方案知道哪一层可以拆。**

---

## 1. 心智模型：三层，三个独立的故障域

```
┌─ 第 3 层  记忆层  AGENTS.md（工作区文件）
│   角色设定 / 已确认事实 / 在场原文片段 / 检索规则
│   坏了会怎样：语气不对、人称跑偏、事实错乱
│   怎么修：改文件 → 开新会话（只在新会话首次请求时加载）
│
├─ 第 2 层  压缩层  dsh-compaction-basic（DSH 自带）
│   到水位才压缩；摘要走 flash；决定「模型看到多少」
│   坏了会怎样：压得太早（贵）、压得太晚（撞窗口报错）
│   怎么修：改 cordis.patch.yml 的 thresholdRatio / retainRatio → 重启生效
│
└─ 第 1 层  归档层  openseek-lcm（第三方插件）+ SQLite
    <DSH_HOME>/storages/dsh-plugin-lcm/lcm.db
    <DSH_HOME>/sessions/**/session.*.jsonl*   ← 原始源头（无损、追加式）
    坏了会怎样：搜不到原文 → 但原文仍在 sessions 里，可重建
    怎么修：/lcm doctor apply → 重启 → 实在不行删 lcm.db 让它重建
```

**关键认知：这三层可以独立替换。**

- 想换记忆方案？只动第 3 层，前两层不用管。
- 嫌压缩不好用？只动第 2 层，归档还在。
- 插件挂了？删 `lcm.db`，原文在 `sessions/` 里，重启后自动重建。

**最坏情况**：全部卸载 → 你退回原生 DSH，**会话记录一条不少**。

## 2. 日常运维

### 每周（30 秒）

```powershell
# 一句话体检
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\dsh-backup.ps1 -WaitIdleMinutes 0
```

看两件事：有没有报错、`archive/lcm.db` 有没有生成。

或者在 DSH 里直接：

```
/lcm status
```

**盯这三个数**：
| 字段 | 健康值 | 异常意味着 |
|---|---|---|
| `capture_failures` | `0` | >0 说明有消息没归档，跑 `/lcm doctor apply` |
| `message_count` | 持续增长 | 不涨 = 插件没在跑（没重启 / profile 装错） |
| `db_bytes` | 缓慢增长 | 涨太快 = 有超大工具结果在灌（考虑 `capture.includeToolResults: false`） |

### 每月

```
/lcm compact apply      # VACUUM，把删掉的页真正还给磁盘（不会删任何消息）
/lcm retention_report   # 预览保留策略会清掉什么（默认什么都不清）
/lcm doctor apply       # 修复 FTS 索引和摘要树
```

### 备份检查

```powershell
Get-ChildItem "$env:USERPROFILE\Documents\dsh-backup" -Directory |
  Sort-Object Name -Descending | Select-Object -First 3 Name, LastWriteTime
```

应该有最近的几个时间戳目录。没有 = 计划任务没跑（看 `idle-scheduler.log`）。

## 3. 诊断树：症状 → 原因 → 修法

### 3.1 `/lcm status` 没反应 / 报未知命令

```
① 没重启 DSH
   → 插件代码只在进程启动时加载。完全退出再开。

② 插件装错 profile
   → 检查 <DSH_HOME>/profiles/<你用的profile>/node_modules/openseek-lcm 是否存在
   → DSH 有 desktop / web / tui 多个 profile，装错很常见

③ 插件加载失败（静默降级）
   → 插件不会让对话失败，而是降级。看 DSH 日志里的 [lcm] 行
   → 常见原因：node:sqlite 不可用（Node < 22.5）
```

### 3.2 `message_count` 不涨

```
① 这个会话是插件装上之前就开的
   → 新开一个会话试试。老会话要等插件 watermark 回填，可能慢。

② capture.enabled = false
   → 检查 patch 里 openseek-lcm 的 config

③ 会话事件没有触发（极少见）
   → 在 DSH 里跑一句 /lcm status，它会主动做一次 ensureCaptured 回填
```

### 3.3 `lcm_grep` 搜不到明明存在的内容

按顺序排查：

```
① 中文搜不到 → 老版本插件（< 0.1.0 没有 CJK bigram 索引）
   → /lcm status 看版本；升级插件

② 关键词太长 → 试试只搜 2-3 个字
   → FTS 索引存的是 bigram（中文）/ trigram（拉丁），超长短语要求全部相邻命中

③ scope 不对 → 你在 A 会话，内容在 B 会话
   → /lcm grep "关键词" --scope worktree（同工作目录）
   → /lcm grep "关键词" --scope root（同分支树）
   → 都找不到：/lcm grep "关键词" --scope all（跨全部归档）

④ 内容在 artifact 里（超长块被外移）
   → /lcm blobstats 看有没有大 blob
   → 用 lcm_artifact 读

⑤ 索引坏了
   → /lcm doctor apply 重建 FTS
```

### 3.4 上下文突然撞窗口报错

```
① 水位设置太高
   → thresholdRatio 降到 0.6 甚至 0.55

② 中文被低估（4 字符/token 的估算）
   → 中文约 1 字 = 1 token，估算值偏小。留缓冲，别贴 0.9

③ 单个不可分单元太大（一次 huge 工具结果）
   → tool-result-pruner 的 thresholdChars 调小（比如 12000）

④ 系统提示 + 工具表本身就很大
   → 减少 tools.expose 白名单里的工具
```

### 3.5 越聊越贵

```
① 缓存没命中
   → 看用量面板的「缓存命中」百分比。低于 80% 就是有问题
   → 检查：是不是每轮都在改系统提示 / 改工具表 / 加时间戳

② 工具调用次数太多（step 数爆炸）
   → 一句话能问完的事，别让它连查 5 次
   → 在 AGENTS.md 里写「一次查 2-3 个关键词，别反复搜」

③ 逐字尾部太大
   → retainRatio 从 0.35 降到 0.25（先动这个，别动 thresholdRatio）
```

### 3.6 角色「像白板」

不是 bug，是机制上限。见 `docs/深入原理.md` §6。

```
修法：AGENTS.md 的 §3「在场记录」写 8-15 段原文片段。
     不是总结，是逐字原话。
     这一层是「检索」和「在场感」之间唯一的桥。
```

## 4. 升级路径

### 4.1 DSH 升级前（每次必做）

```powershell
# 1. 先完整备份
.\scripts\dsh-backup.ps1 -WaitIdleMinutes 0

# 2. 记下当前版本
Get-Content "C:\Users\<你>\AppData\Local\Programs\DeepSeek Harness\version"

# 3. 记下插件版本
(Get-Content "$env:USERPROFILE\.dsh\profiles\desktop\node_modules\openseek-lcm\package.json" | ConvertFrom-Json).version
```

### 4.2 DSH 升级后检查清单

```
□ DSH 能正常启动
□ /lcm status 有输出（插件仍被加载）
□ message_count 还在涨（捕获没断）
□ lcm_grep 能搜到东西（FTS 没坏）
□ 压缩参数仍生效（看 /lcm status 里的配置回显）
□ node tests\acceptance.mjs 还是 17/17
```

**任何一项失败**：先跑 `/lcm doctor apply`，不行就删 `lcm.db` 重启（会自动从 `sessions/` 重建，只是慢）。

### 4.3 插件升级

```powershell
# 关掉 DSH
dsh plugin --profile desktop update openseek-lcm

# 或指定版本
dsh plugin --profile desktop add openseek-lcm@0.1.2
```

**升级后必读它的 README 的「配置」表**——这个项目在 0.1.x 期间改过键名（`dbPath` → `storeDir`，`contextThreshold` 被移除）。**配置键名不匹配会被静默忽略**，症状就是"配了没用"。

**核对方法**：

```powershell
# 看插件实际认哪些键
Get-Content "$env:USERPROFILE\.dsh\profiles\desktop\node_modules\openseek-lcm\lib\config.js" |
  Select-String -Pattern '^\s{2}\w+:' | Select-Object -First 40
```

把你 patch 里的键跟这个列表逐个对。**对不上的就是无效配置。**

## 5. 参数调优

### 5.1 压缩层公式（来自 `dsh-compaction-basic` 源码 `resolveCompactSpec`）

```
阈值     = floor( min( W × thresholdRatio, (W − O) − headroomTokens ) )
逐字保留 = floor( (W − O) × retainRatio )

W = 1,048,576   deepseek-flash 窗口
O = 256,000     请求输出预留（dsh-llm-deepseek 的 maxTokens 默认）
```

**约束**：`retainRatio` 必须 < `thresholdRatio`，否则加载时直接拒绝。

### 5.2 三个旋钮的取舍

| 旋钮 | 调大 | 调小 |
|---|---|---|
| `thresholdRatio` | 压得更晚，省 token，但容易撞窗口 | 压得更早，更安全，但压缩更勤（每次压缩都会让缓存失效一次） |
| `retainRatio` | 逐字留更多，人味更足，但每轮固定成本上升 | 更省，但容易"忘了刚才" |
| `headroomTokens` | 给输出留更多余量，更安全 | 阈值更容易顶到 `W × ratio` |

**调参优先级**：先动 `retainRatio`，再动 `headroomTokens`，最后才动 `thresholdRatio`。
理由：`thresholdRatio` 一低，压缩频率上升，每次都付一笔摘要请求 + 缓存失效，反而更贵。

### 5.3 快速算一下新参数的效果

```powershell
$W=1048576; $O=256000; $r=0.6; $ret=0.35; $h=24576
$thr = [Math]::Floor([Math]::Min($W*$r, ($W-$O)-$h))
$keep = [Math]::Floor(($W-$O)*$ret)
"阈值 $thr token（窗口 $([Math]::Round($thr/$W*100,1))%）"
"逐字保留 $keep token（约 $([Math]::Round($keep/3.2)) 字中文）"
"压缩后每轮固定携带约 $([Math]::Round(($keep+4000)/1000))K token"
```

### 5.4 缓存友好性（比调参更重要）

**唯一原则：请求前缀要稳定。**

- ✅ 系统提示不变
- ✅ 工具表不变（用固定白名单，别按需增删）
- ✅ 变的东西放**末尾**（DSH 把运行时上下文作为单独一条 user 消息追加在最后，这是对的）
- ❌ 每轮改系统提示
- ❌ 每轮往系统提示里插时间戳/环境快照
- ❌ 频繁小压缩（每次都让前缀失效）

## 6. 直接查库（比问模型更快）

### 6.1 表结构（实测，schema v4）

```
sessions        session_id, title, cwd, worktree_key, parent_session_id, root_session_id,
                lineage_depth, pinned, pin_reason, created_at, updated_at, compacted_at,
                deleted, event_count, watermark_seq
messages        message_id, session_id, seq, role, created_at, deleted_at, info_json, text
artifacts       artifact_id, session_id, message_id, block_index, artifact_kind, field_name,
                preview_text, content_text, content_hash, metadata_json, char_count, created_at
artifact_blobs  content_hash, content_text, char_count, created_at, orphaned_at   ← 按内容去重
summary_nodes   node_id, session_id, level, node_kind, start_seq, end_seq,
                message_ids_json, summary_text, strategy, created_at
summary_edges   session_id, parent_id, child_id, child_position                   ← 摘要树的边
summary_state   session_id, archived_count, latest_message_created,
                archived_signature, root_node_ids_json, updated_at               ← 增量构建状态
resumes         session_id, note, updated_at                                      ← resume note
events          id, session_id, event_type, seq, ts, payload_json                 ← 内部事件（可剪枝）
meta            key, value                                                        ← schema_version / created_at
```

FTS5 虚表（都是 `tokenize = "unicode61 tokenchars '_'"`，**content 列里存的是 n-gram 展开后的文本**）：

```
message_fts   (session_id, message_id, role, created_at UNINDEXED, content)
summary_fts   (session_id, node_id, level, created_at UNINDEXED, content)
artifact_fts  (session_id, artifact_id, message_id, artifact_kind, created_at UNINDEXED, content)
```

### 6.2 常用 SQL

用 DSH 自带的 node 跑（它才有 `node:sqlite`）：

```powershell
$node = "$env:USERPROFILE\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\node\bin\node.exe"
$db = "$env:USERPROFILE\.dsh\storages\dsh-plugin-lcm\lcm.db"

# 各会话消息量
& $node -e "const{DatabaseSync}=require('node:sqlite');const d=new DatabaseSync(process.argv[1],{readOnly:true});console.table(d.prepare('select session_id,count(*) msgs,max(created_at) newest from messages group by session_id order by newest desc limit 10').all())" $db
```

或者用仓库里的脚本：

```powershell
node tools/lcm-inspect.mjs          # 体检：完整性 + 计数 + 每会话统计
node tools/lcm-inspect.mjs --sql "select count(*) from messages"
```

**高频查询**：

```sql
-- 某个会话最近的 20 条原文
select role, datetime(created_at/1000,'unixepoch','localtime') t, substr(text,1,120)
  from messages where session_id=? order by seq desc limit 20;

-- 归档里有多少条消息被标了删除
select count(*) from messages where deleted_at is not null;

-- 摘要树每一层的节点数（看树是否在正常生长）
select level, count(*) from summary_nodes where session_id=? group by level order by level;

-- 最大的 artifact（找出是哪个工具输出在灌库）
select artifact_id, char_count, preview_text from artifacts order by char_count desc limit 10;

-- 孤立 blob（可回收的垃圾）
select count(*), sum(char_count) from artifact_blobs where orphaned_at is not null;
```

## 7. 从零重建归档

归档是**派生数据**，随时可重建。

```powershell
# 1. 停 DSH
Get-Process 'DeepSeek Harness' -ErrorAction SilentlyContinue | Stop-Process -Force

# 2. 把旧库挪走（别直接删，先留着观察）
Move-Item "$env:USERPROFILE\.dsh\storages\dsh-plugin-lcm" "$env:USERPROFILE\.dsh\storages\dsh-plugin-lcm.old"

# 3. 启动 DSH —— 插件会自动创建新库，并从 sessions/ 回填
#    回填是懒加载的：你打开哪个会话，才回填哪个
```

**代价**：回填要重读会话日志，几百条消息大概几秒到几十秒。而且**历史会话摘要树要重建**，第一次 `lcm_expand` 会慢。

**什么时候值得重建**：

- FTS 索引坏了且 `/lcm doctor apply` 修不好
- 升级跨了大版本（schema 变更）
- 想丢弃某些误捕获的内容（配合 `privacy.redactPatterns`）

## 8. 如果你想自己写插件（实现思路）

### 8.1 核心只有四个循环

```
① 捕获循环：每个会话事件 → 过滤 → 归一化 → 写库 + 建索引
② 压缩循环：每个请求前 → 测压力 → 到水位就选范围 → 调模型写摘要 → 替换
③ 注入循环：压缩后第一轮 → 生成指针 → 塞进 pre-step 的 decision
④ 检索循环：模型调工具 → FTS 收候选 → JS 重排 → 返回原文片段
```

### 8.2 捕获：必须做的三件脏活

**a) 过滤 harness 注入的消息。** DSH 会把运行时上下文、系统提示更新、工具表、skill 目录…都作为 user/message 提交。不过滤的话，你会把自己的输出再归档一遍，然后召回自己。

需要跳过的 `source.kind`（实测清单）：

```
lcm-recall · runtime-context · system-prompt · agent-instructions
tool-registry · skill-catalog · subagent-settled · compact-checkpoint · goal
```

**原则：只跳"已知的注入来源"，未知的照常捕获。** 猜错方向要选"多存"而不是"漏存"。

**b) 事件形状要按类型分叉。** 不是所有事件都是 `event.data`：

| 事件 | 消息在哪 |
|---|---|
| `user/message` | `event.data` 本身就是消息 |
| `assistant/message` / `tool/result` / `system/message` / `developer/message` | `event.data.message` |

**c) 超大块要外移。** 一个 10 万字符的工具输出会撑爆索引。超过阈值（比如 60000 字符）就写进 `artifacts` 表，消息里存预览 + 引用。**按内容 hash 去重**（同一个文件被读 5 次只存一份）。

### 8.3 索引：中文的坑

**别用默认的 `unicode61`**——它把整串汉字当一个 token，`上下文` 搜不到 `无损上下文记忆`。
**也别直接换 `trigram`**——两字词全废，而两字是中文常态。

正确做法（`openseek-lcm` 用的）：

```javascript
// 建索引时：把原文改写成定长 n-gram
function explodeForIndex(text) {
  // CJK 段 → bigram；拉丁段 → trigram
  // "无损上下文" → "无损 损上 上下 下文"
  // "database" → "dat ata tab aba bas ase"
}
// 用 unicode61 索引这些 gram，tokenchars 加上 '_' 保留标识符下划线
```

查询时同样把 query 展开成 gram，然后要求**这串 gram 相邻出现**——于是"子串匹配"变成了 FTS5 能做的事。

### 8.4 检索：OR 收候选，重排保精度

```javascript
// 错：每个词都 AND，几乎必然零命中
// 对：裸词用 OR 收集候选，带引号的短语用 AND

// 然后用 JS 对「原文」重排，权重：
//   token 覆盖率  > 短语命中 > 角色（user 优先） > 新旧程度
```

**还有一个陷阱**：TF-IDF 类的排序器会给"归档里从未出现的词"最高分（因为它看起来最稀有），结果把整个检索预算花在一个查不到的词上。**查询前先把归档里不存在的词丢掉。**

### 8.5 压缩：选范围的两个不变量

```
① 永远不要遮蔽 surface 节点 0（system prompt）
   → 范围必须从「第一个不是 system/message 的节点」开始

② 不要拆开 assistant(tool-call) 和后续的 tool/result
   → 它们是一个不可分单元，拆了 API 会拒绝
```

选范围时从后往前累加 token，直到达到 `retainTokens` 预算，剩下的就是可压缩区间。

### 8.6 注入：用 `agent/pre-step` 而不是改系统提示

```javascript
ctx.effect(() => ctx.on('agent/pre-step', async function (payload, next) {
  const decision = await next();              // 先让别的监听器跑完
  if (decision?.kind !== 'enter') return decision;
  // ...拼你的注入消息
  return { ...decision, messages: [...decision.messages, myMessage] };
  //       ↑ 必须 spread，decision 里还有别的字段（请求序列标记等）
}, { global: true }));
```

**坑**：

- `{ global: true }` 必须加，否则收不到（事件按 agent/session 作用域派发）
- 用 `function` 不用箭头函数——`this` 是派发作用域，箭头函数会把它绑到 `apply()` 上
- `ctx.effect()` 必须在 `apply()` 的**同步路径**上调用，`await` 之后调会导致整个 fiber 失败

### 8.7 摘要树：为了导航，不是为了替代

```
level 0：每条消息一行短摘要
level 1：每 6 个 level-0 折成一个
level 2：每 6 个 level-1 折成一个
...
```

**必须确定性**：同样输入必须产生同样输出（用稳定 hash 做签名）。否则每次重建都变，增量构建就失效了。

**摘要文本要有预算**：1500 字符的根节点装不下几万条消息。它的用途是"从哪往下钻"，不是"读完就够了"。

### 8.8 必须有的降级路径

```javascript
// 每一处都要包：捕获失败 → 记日志 + 计数 + 继续
try { store.capture(header, events); }
catch (e) { noteFailure('capture', e); }        // 绝不能让对话失败

// 水位线守卫：漏捕能自愈
if (liveSeq - 1 > store.watermark(sessionId)) {
  const snapshot = await ctx.sessionQuery.readSession(sessionId);
  store.capture(snapshot.session, snapshot.events);   // 重放补齐
}
```

**原则：归档是加速层，不是依赖。** 它挂了，对话必须照常进行。

## 10. 什么时候该放弃这套方案

诚实一点，这几种情况它不合适：

- **你要的是"内容完全不出本机"** → 换本地模型，这是硬边界
- **你的会话从来不超过 50 轮** → 压缩根本不会触发，只装归档层就够了
- **你对"在场感"的要求是 1:1 复现** → 只有"全量在上下文"能做到，但那意味着每个字都付费
- **你无法接受第三方插件依赖** → 只保留 `compaction-basic` 参数调整 + 手动备份，归档层换成你自己写的脚本（按 §8 的思路）
